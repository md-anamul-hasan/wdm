# WDM issue register

Status key: **Fixed** = code change + regression test that ran and passed in this audit. **Open** = documented, not fixed.
"Verified on" says where the evidence was produced (all runs: Linux, .NET 10.0.114; see FINAL_AUDIT_REPORT.md for what that cannot cover).

| ID | Sev | Component | Finding | Root cause | Status | Regression test / evidence |
|---|---|---|---|---|---|---|
| AUD-001 | P0 | Engine / resume | Deleting or truncating the partial file while its `.wdm-state` remains made the next run "resume": `StorageWriter` recreated the file as zeros and the download finished as **Completed with zero-filled holes**. | Checkpoint trusted without checking the file on disk. | Fixed | `Resume_WhenPartialFileWasDeleted_...`, `Resume_WhenPartialFileWasTruncated_...` (failed before, pass after) |
| AUD-002 | P0 | Worker | A `206` with a `Content-Range` starting at a different offset than requested was written at the requested offset → silent corruption; download reported complete. | No `Content-Range` validation. | Fixed | `Download_WhenServerReturnsWrongContentRange_FailsInsteadOfCorrupting` (reproduced: no error, corrupt data) |
| AUD-003 | P2 | Worker | 401/403/404/410/416 mid-download were retried 5× with 2-4-8-16-16 s backoff (~46 s) before failing (expired signed URLs are the common case). | All non-2xx treated as transient. | Fixed | `Download_WhenServerRevokesAccessMidway_FailsFast` (3 cases; 46 s before, <10 s after) |
| AUD-004 | P1 | Engine / resume | Resume used `TargetFilePath` and segment table from the JSON checkpoint. A tampered/damaged `.wdm-state` could redirect writes to another path or write outside the file. | Checkpoint treated as trusted input. | Fixed | `Resume_IgnoresTargetFilePathStoredInCheckpoint`, `Resume_WithOutOfRangeSegments_RestartsCleanly` |
| AUD-005 | P2 | Prober | `SanitizeFileName` relied on `Path.GetInvalidFileNameChars()`, which is OS-specific (`\` is valid on Linux). Windows build was safe; behaviour was platform-dependent. | OS-specific API. | Fixed | `SanitizeFileName_StripsTraversalOnEveryPlatform`; the existing `RegressionTests.SanitizeFileName_RemovesUnsafeNames` failed on Linux before, passes now |
| AUD-006 | P2 | IPC | Single pipe instance + no read timeout: any same-user client that connects and stays silent blocks all later handoffs. | Unbounded `ReadAsync`. | Fixed (5 s read timeout) | `Pipe_SilentClient_DoesNotBlockLaterRequests` |
| AUD-007 | P2 | IPC | URLs received over the pipe were not re-validated (`file:`, `ftp:` reached the UI layer). HttpClient would reject them, so not exploitable, but the trust boundary was implicit. | Validation only on the sender side. | Fixed | `Pipe_DropsNonHttpUrlsFromRequests` |
| AUD-008 | P2 | Network | CR/LF in `Cookies`/`Referer`/`User-Agent` reached the wire as an extra header (`TryAddWithoutValidation` does not reject it). Sources are the extension, CLI and same-user IPC, so exploitability is low; defence in depth. | Missing control-character check. | Fixed | `Request_WithCrLfInCookies_CannotInjectHeaders` (reproduced: server received `X-Injected: 1`) |
| AUD-009 | P1 | Native host / store | **The published Chrome Web Store extension (`flnbghmpkajibfdfhbcfhkcjkhlokfgi`) was not authorized by the native host** (`PublishedChromeExtensionIds` was empty; the repo's own `store/chrome/listing.md` lists this as a post-publish step). Installer users of the store extension get "WDM not found" and no handoff. | Post-publish step not done. | Fixed in source; **needs a new release** to reach users. Workaround for current installs: `Wdm.NativeHost.exe --register --extension-id flnbghmpkajibfdfhbcfhkcjkhlokfgi` | `NativeHostManifest_AuthorisesStoreAndSideloadedExtensions`. Not verified in a real Chrome (see BROWSER_COMPATIBILITY.md) |
| AUD-010 | P1 | Engine / durability | Checkpoints were written without flushing the file data they describe (flush happened only at dispose), and the checkpoint was deleted before the final flush. After a power loss/OS crash a resume could skip bytes that never reached disk, or a "finished" file could lack its tail with no checkpoint left to say so. | Ordering of flush vs. checkpoint. | Fixed by design (snapshot → flush → write; flush before checkpoint delete). **Not crash-tested** — power loss cannot be simulated here. |
| AUD-011 | P1 | Extension | Takeover pauses the browser download, then waits on the native host (up to ~10 s while WDM starts). If the MV3 service worker is suspended in that window the browser download stays paused forever. | In-memory state only. | Fixed (handoff journal in `storage.session`, settled on next worker start) | `tests/extension/background.test.mjs` (mocked `chrome`; **not** run in a real browser) |
| AUD-012 | P2 | Extension / Firefox | AMO requires `data_collection_permissions` for new submissions since 2025-11-03. | Missing manifest key. | Fixed (`required: ["none"]`) — **owner must confirm this declaration is accurate** | manifest test; AMO acceptance untested |
| AUD-013 | P2 | Privacy / storage | Cookies and Basic-auth passwords (`DownloadRequestOptions`) are persisted in plaintext in `%APPDATA%\WDM\downloads.json` and next to the download in `*.wdm-state`. | Options serialized wholesale. | **Open** — fixing means a persisted-format change (DPAPI) → needs your approval. Interim: don't use `/` credentials on shared machines. | — |
| AUD-014 | P2 | Design | Target file is preallocated at its final name/size; a crash leaves a full-size, partly-zero file that looks complete in Explorer. Only the sidecar `.wdm-state` says otherwise. | Zero-merge design. | **Open** — a `.wdm-part` suffix changes behaviour/compatibility; proposed in the roadmap. | — |
| AUD-015 | P2 | Handoff semantics | The browser download is cancelled when WDM *receives* the request (pipe delivery), not when it has downloaded anything. POST-initiated or one-time-URL downloads, or cancelling WDM's "add download" dialog, lose the download. The Downloads API exposes no HTTP method to filter on. | Inherent to URL re-fetch handoff. | **Open / documented** | — |
| AUD-016 | P3 | Worker | When `Accept-Ranges` is advertised but Range is ignored (200 to a ranged GET at offset > 0), the whole download fails instead of falling back to one connection. | Hard error by design (safe, not corrupting). | **Open** | existing `PauseAndResume_OnServerIgnoringRange...` covers the safe path |
| AUD-017 | P3 | Prober | Empty (0-byte) files fail when HEAD is rejected: fallback ranged GET `0-0` returns 416. Zero-byte reservation file is left behind if a probe is abandoned. | Edge case. | **Open** | — |
| AUD-018 | P3 | Worker | No `ETag`/`If-Range` check between segments: if the file changes server-side mid-download, segments from two versions can mix. Not enforced because CDNs return inconsistent ETags across edges. | Trade-off. | **Open** | — |
| AUD-019 | P2 | Supply chain | `fetch-tools.ps1` downloads `yt-dlp` from `releases/latest` and ffmpeg from BtbN `latest` with **no checksum/signature check**; they are bundled into the installer. | Unpinned, unverified downloads. | **Open** — needs pinned versions + SHA-256 (and a decision on versions) | — |
| AUD-020 | P2 | CI | `release.yml`: third-party actions pinned to tags (`@v4`, `@v1`), not SHAs; `contents: write` is granted to the whole job incl. signing steps; `choco install innosetup` unpinned; the extension zip includes the `key` and Firefox-only fields. | Convenience. | **Open** | — |
| AUD-021 | P3 | UI | `async void OnAnalyzeGrabberClick` (event handler, acceptable if it catches everything); `App.xaml.cs` blocks on a pipe send at start-up (≤3 s). | — | **Open / unreviewed at runtime** — WPF cannot be built or run on Linux. | — |
| AUD-022 | P3 | Test env | `LaunchArguments_ParsesIdmStyleSwitches` assumed Windows path semantics. | Test | Fixed (expected value computed with `Path.GetFullPath`) | passes |
